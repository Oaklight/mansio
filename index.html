MANSIO · Architecture

多智能体消息总线架构总览

MANSIO 是一个面向多智能体协作的轻量消息总线。两个独立发布的包沿网络边界拆分： mansio 提供服务端（存储、路由、前端、管理面板）， mansio-client 提供智能体 SDK、CLI、MCP 服务与联邦能力。 智能体只通过 HTTP 与服务器通信。

01系统上下文

消费者（LLM、人类、运维）通过交付层进入。交付层之下只有一条通道： MansioClient 经 HTTP REST + SSE 访问 HttpFrontend。 管理面板走独立端口，不经过智能体 API。

02分层架构

每一层只依赖下一层的接口，不依赖具体实现。Frontend 定义 attach / serve_forever / shutdown / address 协议； Backend 是抽象基类，可选能力（频道元数据、删除、监听、在线状态、压缩）以独立 Protocol 混入。

03消息流：发布与推送

一次发布经过认证、结构校验、Bus 路由、后端持久化，再分发给本进程订阅者和远端 SSE 客户端。 其他服务器写入的消息通过后端的 watch 通道回流到 Bus。

04认证与访问控制

认证在 Frontend 中间件完成；授权分两层：结构化的频道命名规则，以及频道存储中的 owner、visibility 与 ACL 条目。 /health 与 /v1/auth/check 是公开路径。 broadcast:* 的写入同时检查频道 owner 与 ACL；频道尚不存在时，首个发布者成为 owner。 授权策略集中在 mansio/authz.py 的 ChannelAuthorizer；Frontend 认证后把发布、查询、订阅、频道列表、删除与 ACL 判定交给它。内置频道类型在创建时写入预设 ACL：dm:* 写入 member，notebook:* / memory:* 写入 owner。dm: 频道名必须恰好是 dm:<a>:<b>，两段都必须是合法 agent id（3–64 位小写字母、数字、连字符，由 shared/types.py 的规则统一校验，与服务端 CLI、管理 API、客户端一致）；发布、建频道、查询、订阅对不合法名称返回 400，建频道与发布共用同一校验器。历史遗留的畸形 dm 行仍按私有频道处理（fail-closed），只有发送者可读。频道元数据路由 GET /v1/channels/<ch>/meta 同样经过授权：scoped token 只能读取自己可读频道的元数据；拒绝时返回与「频道不存在」相同的 404，避免确认私有频道存在。对普通频道与注册前缀频道，策略层查询频道存储（`Bus.check_access`），因此 `visibility="private"`、owner 与 ACL 条目对读写生效；无频道存储的后端（Maildir、NATS）按公开处理。`POST /v1/channels` 套用同一套结构规则：notebook:/memory: 仅命名空间本人，dm: 仅两名参与者，broadcast: 保留给首个发布者（supertoken/no-auth 可预创建），_system:* 拒绝 scoped token。工作队列路由同样受控：claim 需要该频道的 publish 规则，ack 与状态查询需要读权限，拒绝响应与「未认领 / 无状态」一致。supertoken 与 no-auth 在 Frontend 直接放行，不进入该策略。

权限字符串授予的动词类型
readread动词：读取频道与消息
publishpublish动词：发布消息
deletedelete动词：删除消息或频道
managemanage动词：管理频道 ACL 与可见性
viewerread角色预设
memberread, publish角色预设；新 ACL 条目的默认值
ownerread, publish, delete, manage角色预设
writeread, publish旧值，按 member 解释
adminread, publish, delete, manage旧值，按 owner 解释

执行点：授权全部发生在 Frontend 的策略层（ChannelAuthorizer）；Bus 不对消息操作做授权，check_access 只是策略查询。HTTP ACL 端点要求 manage，并接受预设、动词或旧值；broadcast:* 写入检查 publish。check_access(required="write"|"admin") 仍分别映射为 publish / manage。

06语义 API 与频道命名

MansioClient 的语义方法只是频道命名的语法糖。所有状态最终都落在一个普通频道里的消息上， 因此任何后端都无需理解“笔记”“记忆”这些概念。

flowchart LR MC["MansioClient"] MC -->|"channel_send / read / poll"| CH["任意频道"] MC -->|"dm_send / dm_read"| DM["dm:[a]:[b] (按字典序；畸形名 400)"] MC -->|"note_write / note_read"| NB["notebook:[user_id]"] MC -->|"thought_record / thought_read"| TH["notebook:[user_id], msg_type=thought"] MC -->|"memory_store / memory_recall"| MM["memory:[user_id]"] MC -->|"notification_check"| NT["_system:notifications:[user_id]"] MC -->|"broadcast_read"| BC["broadcast:[topic]"] MC -->|"queue_publish / claim / ack"| QU["任意频道 + KV 认领状态"] MC -->|"游标快照"| CU["_system:cursors:[user_id]"]
机制实现位置作用
游标MansioClient._fetch_cursors / _save_cursors，频道 _system:cursors:<user>channel_poll 只返回新消息；游标随每次前进持久化，崩溃后不重复投递
自身消息过滤MansioClient.subscribe / listen / channel_poll / check_unread 默认 include_own=False；channel_read 保持包含自身消息；federation 显式传 include_own=True轮询与订阅默认不把自己的消息当作新消息；需要自回显时显式开启
压缩system_policy.system_channel_policy游标快照只保留最新一条，避免系统频道无界增长
线程消息字段 parent_id / thread_id回复链与扁平线程查询
工作队列queue_publish / queue_claim / queue_ack租约式任务认领；NATS 用 KV 保存认领状态；claim 需 publish 权限，ack/status 需读权限
在线状态认证活动与 SSE 订阅自动刷新；POST /v1/presence/heartbeat 供空闲客户端使用users() 反映真实活跃度；heartbeat 只能代表 token 自身用户
订阅批处理MansioClient.subscribe(coalesce_ms=N)N>0 时按订阅开启滚动窗口，窗口结束以 list[Message] 回调一次；默认 0 逐条投递；unsubscribe 冲刷未决批次，close 丢弃；include_own 过滤在批处理之前；listen/injectors 不变

07联邦与消息注入

FederationLink 位于客户端包：它同时持有两个实例的 MansioClient， 按每个频道建立复制流（双向 / 拉取 / 推送），并提供按需远端读取与发送。当前为实验性的两实例桥接，不支持多跳网格。

08部署形态

形态进程与后端适用场景关键约束
本地开发单进程，SQLite 或 Memory，--no-auth本机多智能体试验仅绑定回环地址
共享服务mansio serve + SQLite，HTTP 前端 + 管理面板团队内多个智能体共享一个总线需要 TokenStore 与管理员密码
嵌入式服务器宿主进程内创建 Bus 与 MansioServer同一进程内的服务端逻辑，不经过网络进程内客户端已移除；跨进程仍需 HTTP；Bus 不承担授权，嵌入者必须在调用前自行检查
分布式后端多个 mansio serve 共享 NATS JetStream跨主机、需要持久化与跨服务器投递NATS 无频道元数据/删除能力；认证需显式 --token-db
